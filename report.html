خلاصهٔ اجرایی

Tirotir یک زبان برنامه‌نویسی متنی فارسی است، نه فریمورک. نسخهٔ 1.1.0 یک مفسر واقعی، زبان مبتنی بر Unicode، ابزار خط فرمان، تحلیل معنایی، سیستم پروژه و ماژول، خروجی گرافیکی SVG، تولید صدای WAV، primitiveهای GUI، افزونهٔ VS Code و Builder ساخت EXE را در یک محصول واحد گرد آورده است.

هدف اصلی زبان، فراهم‌کردن مسیر ساده برای شروع و حفظ امکان ساخت برنامه‌های واقعی است. نخستین برنامه می‌تواند فقط این باشد:

چاپ -سلام دنیا-

اما هستهٔ فعلی از متغیر، شرط، حلقه، تابع، فهرست، فرهنگ، ورودی و خروجی، فایل‌های چندماژوله و diagnostics ساختاریافته نیز پشتیبانی می‌کند.

نسخهٔ 1.1.0 در baseline فعلی با ۲۴۴ تست موفق تثبیت شده است. این baseline immutable است. پسوند رسمی زبان .t است و .tirotir فقط برای backward compatibility نگه داشته شده است.

نتیجهٔ کوتاه: Tirotir اکنون یک زبان برنامه‌نویسی فارسی قابل نصب و قابل استفاده در Windows است که ابزارهای پیرامونی خلاقانه دارد؛ اما هنوز نباید آن را یک framework کامل، یک محیط توسعهٔ کامل مانند IDEهای بالغ، یا یک زبان دارای animation و object model کامل معرفی کرد.

هستهٔ زبان در src/tirotir/core.py قرار دارد. تحلیل معنایی در semantic.py از interpreter جداست. قراردادهای معماری در contracts.py تعریف شده‌اند. سرویس Audio در audio.py و Builder در builder.py قرار دارد. سیستم پروژه و ماژول در پوشهٔ src/tirotir/modules/ پیاده‌سازی شده است.

این جداسازی مهم است، زیرا Graphics، Audio و GUI به‌عنوان قابلیت‌های پیرامونی و runtime service دیده می‌شوند، نه به‌عنوان syntaxهای مستقل و غیرقابل‌توسعهٔ زبان.

شناسه و متن فارسی

Lexer از شناسه‌های Unicode پشتیبانی می‌کند. نام متغیر، تابع و کلید فرهنگ می‌تواند فارسی باشد. اعداد فارسی مانند ۲۰ و جداکنندهٔ اعشار فارسی نیز normalize می‌شوند. متن‌های رشته‌ای در syntax فعلی با دو خط تیره نوشته می‌شوند:

چاپ -سلام دنیا-

نرمال‌سازی داخلی، شکل‌هایی مانند ي و ك را به شکل فارسی استاندارد نزدیک می‌کند و Zero Width Non-Joiner را برای سازگاری syntax به underscore تبدیل می‌کند.

تابع‌ها می‌توانند مقدار بازگردانند، تابع پیش از محل فراخوانی تعریف شود یا در semantic analysis برای forward call و recursion ثبت شود. تعداد آرگومان‌ها پیش از اجرا بررسی می‌شود.

قابلیت‌هایی که عمداً ادعا نمی‌شوند

در Tirotir 1.1.0 syntax و runtime کامل برای کلاس، شیء، inheritance، constructor، method dispatch، exception handling عمومی، generator، async/await و type system وجود ندارد. این موارد نباید به‌عنوان قابلیت موجود معرفی شوند.

تحلیل معنایی و diagnostics

Semantic layer مستقل از interpreter است و بدون side effect روی AST عبور می‌کند. این لایه موارد زیر را بررسی می‌کند:

  • نام تعریف‌نشده؛
  • تعریف تکراری؛
  • تغییر ثابت؛
  • استفادهٔ نامعتبر از بازگردان بیرون تابع؛
  • استفادهٔ نامعتبر از بیرون یا ادامه بیرون حلقه؛
  • تعداد آرگومان نادرست تابع؛
  • builtinهای مربوط به GUI، Graphics و Audio.

diagnosticها ساختاریافته‌اند و شامل code، severity، type، message، SourceSpan و suggestion می‌شوند. کدهای ثبت‌شدهٔ semantic در محدودهٔ TIR2001 تا TIR2007 هستند. خطاهای ماژول در محدودهٔ TIR3001 تا TIR3003 قرار دارند و خطای محیط GUI با TIR4001 گزارش می‌شود.

نمونهٔ خطای طراحی‌شده برای کاربر فارسی:

متغیر «نتیچه» پیدا نشد.
پیشنهاد: ابتدا آن را با «بگذار» تعریف کن.

قراردادهای معماری 2.0

بخش Contract Freeze در کنار زبان نسخهٔ 1.1 تثبیت شده است و شامل این مفاهیم است:

  • SourceSpan برای مکان منبع؛
  • Diagnostic برای خطاهای قابل مصرف توسط CLI و ابزارها؛
  • NodeId برای شناسهٔ پایدار AST؛
  • RuntimeService به‌عنوان قرارداد سرویس‌های runtime؛
  • Capability و CapabilityRegistry برای کنترل قابلیت‌ها؛
  • قرارداد سازگاری LANGUAGE_V1 = 1.1.

حالت پیش‌فرض capability فقط core را فعال می‌کند. قابلیت‌های graphics، audio، gui، project-files و network به‌صورت مفهومی جدا شده‌اند و می‌توانند در sandbox یا project configuration کنترل شوند.

CLI و ابزار خط فرمان

پس از نصب بسته، فرمان اصلی tirotir است. جدول کامل فرمان‌ها در بخش ⚡ فرمان‌ها در بالای همین صفحه آمده است.

گزینه‌های عمومی شامل --scene برای مسیر SVG، --play-audio برای تلاش جهت پخش صوت و --live-scene برای خروجی JSON شامل صحنه هستند.

REPL، AST و formatter

REPL با tirotir repl باز می‌شود و کاربر می‌تواند عبارت‌ها را به‌صورت تعاملی اجرا کند. برای خروج از REPL مقدار خروج نوشته می‌شود.

فرمان AST، ساختار parseشده را به JSON تبدیل می‌کند و برای آموزش parser، ابزارهای توسعه و بررسی syntax قابل استفاده است. Formatter فعلی یک formatter سبک است که trailing whitespace و line ending را یکدست می‌کند؛ formatter عمیق و style engine کامل در این نسخه ادعا نمی‌شود.

سیستم پروژه و ماژول

پروژهٔ چندفایلی با tirotir.toml تعریف می‌شود:

[project]
name = "my-project"
entry = "main.t"
language = "2.0"

[capabilities]
graphics = false
audio = false
gui = false
project-files = false
network = false

واردکردن ماژول با syntax زیر انجام می‌شود:

وارد کن -lib/tools-

سیستم ماژول اجزای زیر را دارد:

  • ModuleId برای هویت canonical ماژول؛
  • ModuleSpec برای source و importها؛
  • ModuleGraph برای node و edge؛
  • ModuleLoader برای resolve و load؛
  • ModuleGraphBuilder برای ساخت graph پیش از اجرای source؛
  • ModuleCache برای cache؛
  • sandbox path برای جلوگیری از خروج از project root؛
  • namespace بر پایهٔ مسیر نسبی؛
  • تشخیص cycle با diagnostic TIR3001؛
  • تشخیص module not found با TIR3002؛
  • تشخیص مسیر module نامعتبر با TIR3003.

Graph ابتدا ساخته و بررسی می‌شود و سپس ماژول‌ها در topological order اجرا می‌شوند.

Runtime و امنیت

runtime از import آزاد Python، eval، exec، shell، شبکه و دسترسی آزاد به filesystem پشتیبانی نمی‌کند. سرویس‌ها باید از capabilityهای مشخص عبور کنند.

این ویژگی به‌معنای sandbox امنیتی کامل در سطح سیستم‌عامل نیست. برای اجرای فایل‌های ناشناس یا پروژه‌های غیرقابل اعتماد همچنان باید از حساب کاربری محدود و محیط ایزولهٔ Windows استفاده شود.

محدودیت Graphics

Graphics نسخهٔ 1.1.0 یک renderer استاتیک SVG است. timeline animation، event animation، motion system کامل و نمایش پیشرفتهٔ تعاملی در این نسخه وجود ندارد. این حوزه در baseline به‌عنوان Known Limitation ثبت شده و رفع آن نباید Audio، GUI، Builder، EXE یا .t را تغییر دهد.

Audio

Audio بدون dependency اجباری، موج صوتی را با کتابخانهٔ استاندارد wave تولید می‌کند. render_sequence نت‌ها را به یک WAV پیوسته تبدیل می‌کند. نرخ پیش‌فرض 44,100 هرتز و خروجی mono با sample width دو بایت است.

نت‌های فارسی فعلی: دو، ر، رِ، می، فا، سل، لا، سی.

نت بنواز با ۴۴۰ و ۰٫۱۵
نت بنواز با -دو- و ۰٫۱۵

پخش مستقیم به backend سیستم‌عامل وابسته است:

  • Windows: PowerShell Media.SoundPlayer؛
  • macOS: afplay؛
  • Linux: aplay، paplay یا ffplay در صورت نصب.

اگر backend پخش وجود نداشته باشد، فایل WAV حفظ می‌شود و runtime پیام فارسی مناسب می‌دهد.

محدودیت GUI

primitiveهای ساخت پنجره و widgetهای پایه موجودند. سیستم event کامل، callback فارسی برای دکمه، binding داده، designer بصری، layout engine پیشرفته و canvas مشترک با SVG در این نسخه کامل نشده‌اند. اجرای GUI به desktop واقعی و Tkinter نیاز دارد. در محیط headless diagnostic TIR4001 تولید می‌شود.

VS Code و افزونهٔ tirotirLang

افزونهٔ مستقل با نام tirotirLang ساخته شده است. association رسمی آن برای پسوند .t است. امکانات فعلی:

  • شناسایی فایل‌های .t؛
  • syntax highlighting؛
  • فرمان اجرا؛
  • فرمان check؛
  • نمایش AST؛
  • خروجی فارسی راست‌به‌چپ؛
  • نمایش live scene در WebView؛
  • اتصال به CLI نصب‌شده؛
  • نمایش خروجی متن و قاب صحنهٔ SVG.

WebView با Content Security Policy و JSON.parse برای پروتکل live scene سخت‌سازی شده است. خروجی متن با dir="rtl" نمایش داده می‌شود و source code از نظر منطقی reorder نمی‌شود.

افزونهٔ VS Code، LSP کامل، completion پیشرفته، hover، definition/reference و DAP debugger کامل نیست. این موارد در roadmap ابزار توسعهٔ 2.0 قرار دارند.

Tirotir Builder و ساخت EXE

tirotir builder ابزار GUI ساخت EXE است. Builder فایل اصلی .t، نام برنامه، حالت one-file یا folder، نمایش console، icon و مسیر خروجی را دریافت می‌کند.

Builder source برنامه را در entrypoint موقت جاسازی می‌کند و آن را به PyInstaller می‌دهد.

محدودیت EXE

native Windows build باید روی خود Windows انجام شود، زیرا PyInstaller به‌طور معمول برای سیستم‌عامل مقصد build می‌کند. Builder prototype عملیاتی است، اما installer کامل و امضاشدهٔ Windows با نام Tirotir-1.1.0-Setup.exe باید جداگانه با ابزارهایی مانند Inno Setup بسته‌بندی شود.

سه artifact متمایز:

  • tirotir.exe ابزار زبان است؛
  • program.exe خروجی یک برنامهٔ کاربر است؛
  • Setup.exe نصب‌کنندهٔ محصول است.

محدودیت‌های شناخته‌شده

محدودیت‌های زبان

کلاس، شیء، inheritance، exception model عمومی، type system، async runtime و generator در نسخهٔ فعلی وجود ندارند.

محدودیت‌های Graphics

renderer فعلی SVG است و animation timeline یا event-driven motion کامل وجود ندارد.

محدودیت‌های Audio

تولید WAV مستقل است، اما پخش مستقیم به backend سیستم‌عامل و ابزارهای موجود وابسته است.

محدودیت‌های GUI

Tkinter و desktop نیاز است و event/callback کامل هنوز وجود ندارد.

محدودیت‌های VS Code

LSP و DAP کامل، completion عمیق، hover و navigation حرفه‌ای هنوز ساخته نشده‌اند.

محدودیت‌های EXE و Setup

ساخت native EXE و Setup باید روی Windows انجام و روی Windows پاک آزمایش شود. Builder فعلی با installer عمومی یکی نیست و امضای Authenticode به‌صورت خودکار وجود ندارد.

محدودیت‌های مستندات تاریخی

برخی مستندات قدیمی repository ممکن است اعداد تاریخی مانند ۲۴۰ تست یا ۷۱ نمونه را ذکر کنند. برای وضعیت فعلی، Baseline Freeze و آخرین quality gate مرجع هستند: ۲۴۴ تست در baseline و بستهٔ آموزشی مستقل با ۴۱ فایل .t.

معماری پیشنهادی مرحلهٔ بعد

پس از freeze، مرحلهٔ بعد باید در branch مستقل و فقط روی scope تأییدشده انجام شود. برای Examples، اولویت مناسب افزایش آموزش و پوشش کاربردی بدون تغییر runtime است.

برای توسعهٔ زبان در مسیر 2.0، ترتیب منطقی:

  1. تثبیت قراردادهای موجود؛
  2. تکمیل semantic spans و diagnostics؛
  3. تکمیل module semantics؛
  4. تبدیل Event Runtime پایه به runtime قابل استفاده از source؛
  5. طراحی object model واقعی؛
  6. LSP؛
  7. debugger و DAP؛
  8. سپس بررسی IR، bytecode و VM اختیاری.
EventLoop، EventQueue و HandlerRegistry اکنون به‌صورت زیرساخت مستقل Python وجود دارند و تست شده‌اند؛ اما syntax رویدادمحور کامل و اتصال عمومی آن‌ها به برنامه‌های Tirotir هنوز جزو قابلیت نهایی 1.1.0 نیست.

جمع‌بندی نهایی

Tirotir 1.1.0 اکنون از مرحلهٔ نمونهٔ ساده عبور کرده و یک زبان برنامه‌نویسی فارسی واقعی با مفسر، semantic layer، پروژهٔ چندفایلی، CLI، VS Code، Graphics SVG، Audio WAV، GUI Tkinter و Builder EXE است.

مهم‌ترین ارزش محصول در این مرحله، ترکیب مسیر شروع ساده با هستهٔ واقعی و قابل تست است. کاربر می‌تواند از چاپ -سلام دنیا- شروع کند، سپس به متغیر، شرط، حلقه، تابع، فهرست، فرهنگ و پروژهٔ چندفایلی برسد.

در کنار این توانایی‌ها، مرزهای محصول نیز روشن هستند. Graphics هنوز Known Limitation دارد. GUI یک backend اولیه است. Audio playback محیط‌محور است. LSP، DAP، class/object و animation کامل هنوز وجود ندارند. این محدودیت‌ها بخشی از صداقت release هستند و نباید در معرفی عمومی پنهان شوند.
