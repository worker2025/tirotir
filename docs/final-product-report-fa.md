# گزارش جامع محصول تیروتیر ۱٫۰

**نام محصول:** تیروتیر (Tirotir)  
**نسخه:** ۱٫۰٫۰  
**زبان پیاده‌سازی:** Python 3.9 یا بالاتر  
**پسوند برنامه‌ها:** `.t`  
**CLI:** `tirotir`  
**اکستنشن VS Code:** `tirotirLang`

## خلاصهٔ مدیریتی

تیروتیر در وضعیت فعلی یک زبان کوچک اما واقعی، مفسری و قابل نصب است. کاربر می‌تواند فایل `.t` بسازد، آن را از طریق CLI اجرا کند، AST را به JSON ببیند، برنامه را بررسی و قالب‌بندی کند و از REPL استفاده کند. هستهٔ زبان از شناسه‌ها و اعداد فارسی پشتیبانی می‌کند و بلوک‌ها را با تورفتگی تشخیص می‌دهد.

نسخهٔ حاضر برای آموزش مبانی برنامه‌نویسی مناسب است، اما هنوز یک زبان عمومی یا محیط توسعهٔ کامل محسوب نمی‌شود. مهم‌ترین مسیر نسخهٔ بعدی باید بهبود تجربهٔ توسعه، استانداردسازی کتابخانهٔ استاندارد، تکمیل ابزارهای VS Code و افزودن قابلیت‌های چندرسانه‌ای به‌صورت ماژولار و امن باشد.

> **نتیجهٔ اصلی:** برای افزودن ایموجی، رسم شکل و پخش صدا لازم نیست زبان از ابتدا بازنویسی شود. بهترین راه، تعریف یک API استاندارد در خود تیروتیر و پیاده‌سازی backendهای آن با کتابخانه‌های Python است. برنامهٔ تیروتیر نباید مستقیماً Python را import کند.

## ۱. امکانات موجود در نسخهٔ ۱٫۰

### ۱.۱ زبان و نحو

تیروتیر از کلیدواژه‌های فارسی و شناسه‌های فارسی پشتیبانی می‌کند. اعداد فارسی و لاتین پذیرفته می‌شوند و نیم‌فاصله در شناسه‌ها به زیرخط نرمال می‌شود. زبان بر پایهٔ تورفتگی است و برای بلوک‌های شرط، حلقه، تابع و فرهنگ به آکولاد نیاز ندارد.

متن با خط تیرهٔ جفتی نوشته می‌شود؛ برای نمونه `-سلام جهان-`. خط تیرهٔ داخل متن با `\\-` قابل گریز دادن است. کامنت با `#` شروع می‌شود و اجرا نمی‌شود.

### ۱.۲ متغیر، ثابت و انتساب

دو نحو انتساب پشتیبانی می‌شود:

```text
بگذار نتیجه برابر ۱۰ + ۵
نتیجه = نتیجه + ۱
```

ثابت با `ثابت` تعریف می‌شود و تغییر آن خطای زمان اجرا ایجاد می‌کند.

### ۱.۳ نوع‌های داده

نسخهٔ حاضر عدد، متن، مقدار منطقی، تهی، فهرست و فرهنگ را پشتیبانی می‌کند. فهرست امکان خواندن، تغییر عضو، پیمایش و افزودن و حذف عضو از طریق توابع کمکی را دارد. فرهنگ با بلوک تورفته ساخته می‌شود:

```text
بگذار شخص برابر فرهنگ
    نام برابر -سارا-
    سن برابر ۲۴

چاپ شخص نام
چاپ شخص[سن]
```

### ۱.۴ عبارت‌ها و کنترل جریان

عملگرهای `+`، `-`، `*`، `/` و `%` با اولویت استاندارد پیاده‌سازی شده‌اند. مقایسهٔ نمادی و فارسی قابل استفاده است؛ برای نمونه `>=` و `بزرگتر یا مساوی` هر دو پشتیبانی می‌شوند. منطق با `و`، `یا` و `نه` فراهم است.

شرط‌های `اگر`، `وگرنه اگر` و `وگرنه`، حلقهٔ `برای`، حلقهٔ `تاوقتی`، `بیرون` و `ادامه` در دسترس هستند. برای محافظت در برابر حلقهٔ بی‌نهایت سقف تعداد گام‌های اجرا اعمال می‌شود.

### ۱.۵ تابع و بازگشت

تابع می‌تواند پارامتر، متغیر محلی، شرط، حلقه و مقدار بازگشتی داشته باشد. تعداد آرگومان‌ها بررسی می‌شود و recursion در حد محدودیت اجرای مفسر پشتیبانی می‌شود.

### ۱.۶ ورودی، خروجی و کتابخانهٔ کوچک داخلی

`چاپ` برای خروجی و `بخوان` برای ورودی استفاده می‌شود. توابع داخلی نسخهٔ حاضر شامل `طول`، `افزودن`، `حذف`، `به_عدد` و `به_متن` هستند. این توابع عمداً محدودند و دسترسی آزاد به سیستم‌عامل یا شبکه ندارند.

### ۱.۷ معماری فنی

مسیر اجرای برنامه به شکل زیر است:

```text
متن منبع
  ↓
نرمال‌سازی Unicode
  ↓
تشخیص تورفتگی و تولید توکن
  ↓
Parser
  ↓
AST
  ↓
Interpreter
  ↓
خروجی یا خطای فارسی
```

AST به JSON تبدیل می‌شود. این تصمیم امکان ساخت formatter، زبان‌سرور، debugger و ابزارهای تحلیل ایستا را در نسخه‌های آینده فراهم می‌کند.

### ۱.۸ CLI و بسته‌بندی

فرمان‌های فعلی عبارت‌اند از:

```text
tirotir run program.t
tirotir check program.t
tirotir ast program.t
tirotir format program.t
tirotir format program.t --write
tirotir repl
tirotir version
tirotir program.t
```

پروژه با `pyproject.toml` بسته‌بندی شده است و با `pip install .` یا `pip install -e .` نصب می‌شود. استفاده از entry point در بستهٔ Python، روش استاندارد ایجاد فرمان اجرایی پس از نصب است [1].

### ۱.۹ امنیت

برنامه‌های تیروتیر نمی‌توانند مستقیماً shell، import پایتون، فایل‌سیستم، شبکه یا فرمان سیستم را اجرا کنند. این محدودیت برای زبان آموزشی ضروری است. مفسر همچنین سقف اجرای گام‌ها دارد، هرچند محدودیت حافظه و زمان در سطح فرایند هنوز کامل نشده است.

### ۱.۱۰ آزمون و اعتبارسنجی

در نسخهٔ نهایی ۲۰۲ تست خودکار موفق است. این تست‌ها lexer، parser، interpreter، Unicode، اعداد فارسی، شرط، حلقه، تابع، recursion، فهرست، فرهنگ، ورودی، انتساب با `=`، خطاهای اصلی و حفاظت حلقهٔ بی‌نهایت را پوشش می‌دهند. ۷۱ برنامهٔ نمونه نیز از طریق CLI اجرا شده‌اند. نام فایل همهٔ نمونه‌های رسمی انگلیسی است تا در Windows، Linux، macOS و ابزارهای توسعه سازگاری بیشتری داشته باشد.

## ۲. امکانات اکستنشن VS Code

اکستنشن `tirotirLang` فایل‌های `.t` را شناسایی می‌کند، برای کلیدواژه‌ها، متن، عدد، کامنت و عملگرها رنگ‌بندی TextMate ارائه می‌دهد و تورفتگی بلوک‌های زبان را بهتر می‌کند. VS Code برای رنگ‌بندی پایه از TextMate grammar استفاده می‌کند و برای تحلیل عمیق‌تر می‌تواند از semantic tokens یا Language Server استفاده کند [2] [3].

سه فرمان در اکستنشن وجود دارد:

- اجرای فایل؛
- بررسی فایل؛
- نمایش AST.

اکستنشن فعلی خروجی این فرمان‌ها را در ترمینال VS Code نشان می‌دهد. این ترمینال برای فارسی و متن ترکیبی همیشه راست‌به‌چپ واقعی را تضمین نمی‌کند؛ بنابراین این بخش باید در نسخهٔ بعدی اصلاح شود.

## ۳. کمبودها و ریسک‌های نسخهٔ ۱٫۰

### ۳.۱ تحلیل معنایی کامل نیست

Parser و interpreter بسیاری از خطاها را تشخیص می‌دهند، اما تحلیل جداگانهٔ semantic هنوز به‌صورت یک مرحلهٔ مستقل وجود ندارد. در نتیجه بخشی از خطاها هنگام اجرا آشکار می‌شود، نه پیش از اجرا. پیشنهاد می‌شود در نسخهٔ بعد یک Symbol Table و pass تحلیل معنایی ساخته شود.

### ۳.۲ خطاها هنوز کاملاً ساختاریافته نیستند

پیام‌های خطا فارسی هستند، اما بهتر است هر خطا شیء مشخصی با نوع، خط، ستون، قطعهٔ کد، علت، پیشنهاد اصلاح و کد خطا داشته باشد. این ساختار برای نمایش زیرخط قرمز در VS Code و تولید JSON diagnostics لازم است.

### ۳.۳ formatter فعلی ساده است

formatter فعلی پایان خط و بخشی از فاصله‌ها را استاندارد می‌کند، اما formatter کامل برای تورفتگی، فاصلهٔ عملگرها، فرهنگ، فهرست و متن هنوز لازم است. formatter باید AST-based باشد تا بدون تغییر معنای برنامه کار کند.

### ۳.۴ ورودی و محیط اجرا

`بخوان` به ورودی استاندارد متصل است، اما prompt فارسی، تبدیل مستقیم به عدد و کنترل زمان انتظار هنوز API استاندارد ندارد. مفسر همچنین sandbox کامل فرایندی با محدودیت حافظه و timeout خارجی ندارد.

### ۳.۵ پوشش سیستم‌عامل

بستهٔ Python روی Windows، Linux و macOS قابل نصب است، اما تست خودکار واقعی روی هر سه سیستم‌عامل و installer مستقل `.exe`، `.msi` یا بستهٔ macOS هنوز تهیه نشده است.

### ۳.۶ اکستنشن هنوز Language Server نیست

اکستنشن فعلی syntax highlighting و اجرای فرمان دارد، اما تکمیل هوشمند، رفتن به تعریف، rename symbol، diagnostics لحظه‌ای، hover documentation و debugging واقعی ندارد. برای این قابلیت‌ها باید Language Server Protocol یا یک سرویس اختصاصی ساخته شود.

### ۳.۷ ابهام نحو متن با تفریق

قاعدهٔ متن با `-...-` ساده و آموزشی است، اما در برخی عبارت‌های پیچیده می‌تواند با تفریق مبهم شود. نسخهٔ بعد بهتر است علاوه بر این نحو، متن استاندارد با کوتیشن فارسی یا لاتین را به‌صورت اختیاری اضافه کند؛ برای نمونه `"سلام"` یا `«سلام»`.

## ۴. پاسخ فنی دربارهٔ ایموجی، رسم و موسیقی

### ۴.۱ کنترل و نمایش ایموجی

نمایش ایموجی از نظر زبان ساده است، زیرا ایموجی یک نویسه یا رشتهٔ Unicode است:

```text
چاپ -سلام 🙂-
```

این قابلیت به کتابخانهٔ جدید نیاز ندارد، اما شکل نمایش به فونت و terminal وابسته است. اگر منظور کنترل ایموجی در یک رابط گرافیکی باشد، باید API گرافیکی داشته باشیم. برای نسخهٔ آموزشی بهتر است ابتدا این توابع تعریف شوند:

```text
نمایش_ایموجی با -🙂-
پاک_کردن_صفحه
```

پیاده‌سازی backend می‌تواند در ابتدا خروجی متنی باشد و بعداً به پنجرهٔ گرافیکی یا WebView منتقل شود.

### ۴.۲ رسم اشکال هندسی

دو مسیر فنی وجود دارد. مسیر اول استفاده از `turtle` است. این مسیر برای آموزش مناسب است و رسم خط، مربع، دایره، رنگ و حرکت را ساده می‌کند. مستندات رسمی Python ماژول turtle را به‌عنوان محیطی آموزشی برای رسم معرفی می‌کند [4]. مسیر دوم استفاده از SVG یا Canvas در WebView است. این مسیر برای اکستنشن VS Code و نمایش راست‌به‌چپ مناسب‌تر است، زیرا خروجی وب کنترل دقیق روی اندازه، رنگ و جهت متن دارد.

API پیشنهادی زبان:

```text
پنجره بازکن با ۸۰۰ و ۶۰۰
رنگ قلم برابر -آبی-
حرکت با ۱۰۰
چرخش با ۹۰
مربع با ۵۰
دایره با ۳۰
پنجره ببند
```

در نسخهٔ اول گرافیک، پیشنهاد می‌شود backend SVG انتخاب شود. SVG به فایل یا WebView تبدیل می‌شود و به محیط دسکتاپ خاصی وابسته نیست. برای حالت آموزشی ساده می‌توان backend اختیاری turtle را نیز اضافه کرد.

### ۴.۳ پخش نت و موسیقی

برای تولید نت‌های ساده، یک API `نت` با فرکانس، مدت و شدت کافی است. برای پخش فایل صوتی و موسیقی، می‌توان از یک backend اختیاری مانند `pygame.mixer.music` استفاده کرد؛ این API برای بارگذاری و کنترل پخش موسیقی مستند شده است [5].

API پیشنهادی:

```text
نت بنواز با ۴۴۰ و ۰٫۵
موسیقی پخش کن با -آهنگ.wav-
موسیقی توقف کن
```

پشتیبانی از فایل باید کاملاً کنترل‌شده باشد. برنامهٔ تیروتیر نباید مسیر دلخواه سیستم را بدون اجازه بخواند. بهتر است فقط فایل‌های داخل پوشهٔ پروژه یا پوشهٔ `assets` مجاز باشند.

### ۴.۴ آیا باید کتابخانهٔ جدیدی ساخته شود؟

برای هر قابلیت نباید یک زبان جدید یا کتابخانهٔ بزرگ جدا ساخته شود. راه درست ایجاد یک **کتابخانهٔ استاندارد تیروتیر** با API فارسی و backendهای Python است:

```text
tirotir.std.text
 tirotir.std.list
 tirotir.std.graphics
 tirotir.std.audio
 tirotir.std.ui
```

هر ماژول باید یک interface کوچک و پایدار داشته باشد. برنامهٔ تیروتیر فقط API فارسی را ببیند و از Python یا کتابخانه‌های زیرساختی خبر نداشته باشد.

### ۴.۵ آیا مبدل به Python لازم است؟

مبدل کامل به Python در نسخهٔ بعد ضروری نیست. سه گزینه وجود دارد:

| روش | مزیت | ضعف | پیشنهاد |
|---|---|---|---|
| مفسر مستقیم فعلی | ساده، امن و مناسب آموزش | سرعت کمتر | روش اصلی نسخهٔ ۱٫۱ |
| transpiler به Python | دسترسی آسان به کتابخانه‌های Python | خطر ورود API ناامن و دشواری خطاها | فقط backend کنترل‌شده |
| bytecode یا compiler اختصاصی | سرعت و کنترل بالا | هزینهٔ توسعه زیاد | مرحلهٔ بلندمدت |

پیشنهاد عملی این است که تیروتیر همچنان با interpreter اجرا شود و برای قابلیت‌های گرافیک و صدا از adapterهای Python استفاده کند. اگر بعدها سرعت لازم شد، AST موجود می‌تواند به IR یا Python محدود ترجمه شود.

> استفاده از کتابخانهٔ Python باید از طریق توابع ثبت‌شده و whitelist انجام شود، نه با `import` آزاد در برنامهٔ تیروتیر.

## ۵. راه‌حل خروجی راست‌به‌چپ برای اکستنشن

### ۵.۱ مشکل ترمینال

ترمینال VS Code و Windows Terminal در نمایش متن فارسی ساده معمولاً قابل قبول‌اند، اما برای ترکیب فارسی، عدد، نشانه و متن انگلیسی، رفتار BiDi همیشه پایدار نیست. قرار دادن نویسه‌های Unicode مانند RLE و PDF ممکن است در یک ترمینال نتیجهٔ مطلوب بدهد، اما در pipe، log و محیط‌های دیگر ترتیب متن را خراب می‌کند. بنابراین نباید خروجی اصلی زبان را به این علامت‌ها وابسته کرد.

### ۵.۲ راه‌حل پیشنهادی نسخهٔ بعد

اکستنشن باید یک **پنل خروجی RTL مبتنی بر WebView** داشته باشد. WebView می‌تواند HTML را با `dir="rtl"`، `lang="fa"` و فونت فارسی نمایش دهد. خروجی اجرای برنامه به‌جای عبور صرف از ترمینال، از طریق یک کانال امن به WebView فرستاده می‌شود.

ساختار پیشنهادی:

```text
Tirotir CLI
   ↓ stdout / stderr UTF-8
Extension Host
   ↓ پیام کنترل‌شده
WebView Output Panel
   ↓
HTML با dir="rtl"
```

نمونهٔ CSS و HTML مورد نیاز:

```html
<div class="output" dir="rtl" lang="fa"></div>
```

```css
.output {
  direction: rtl;
  unicode-bidi: plaintext;
  white-space: pre-wrap;
  font-family: Vazirmatn, Tahoma, sans-serif;
}
```

در این طراحی، editor کد همچنان متن منطقی Unicode را نگه می‌دارد و فقط نمایش خروجی و خطا RTL می‌شود. این نکته مهم است، زیرا تغییر ترتیب داخلی کد می‌تواند lexer و copy/paste را خراب کند.

### ۵.۳ diagnostics راست‌به‌چپ

در نسخهٔ بعد، خطاها باید به شکل زیر در WebView نشان داده شوند:

- عنوان فارسی خطا؛
- شمارهٔ خط و ستون؛
- قطعهٔ کد؛
- محل خطا با highlight؛
- علت و پیشنهاد اصلاح.

برای underline داخل editor باید از `DiagnosticCollection` اکستنشن یا Language Server استفاده شود. WebView برای گزارش زیبا مناسب است، اما جایگزین diagnostics بومی VS Code نیست.

## ۶. پیشنهاد دقیق برای نسخهٔ ۱٫۱

نسخهٔ ۱٫۱ بهتر است روی تجربهٔ توسعه و کتابخانهٔ استاندارد تمرکز کند، نه روی قابلیت‌های پراکنده. اولویت‌ها به ترتیب زیر پیشنهاد می‌شوند:

### اولویت اول: ابزار توسعه

یک تحلیل‌گر معنایی مستقل ساخته شود. خطاها به شکل ساختاریافته تولید شوند. اکستنشن diagnostics لحظه‌ای، تکمیل کلیدواژه و hover فارسی داشته باشد. formatter واقعی AST-based شود.

### اولویت دوم: خروجی و RTL

پنل خروجی WebView با RTL واقعی اضافه شود. خطاهای فارسی در این پنل نمایش داده شوند. گزینه‌ای مانند `TirotirLang: اجرای فایل در پنل RTL` در اکستنشن ارائه شود. ترمینال به‌عنوان fallback باقی بماند.

### اولویت سوم: کتابخانهٔ استاندارد

ماژول‌های `متن`، `فهرست`، `ریاضی`، `زمان`، `تصادفی` و `ورودی` به شکل API مستند اضافه شوند. هر ماژول باید تست و محدودیت امنیتی مشخص داشته باشد.

### اولویت چهارم: گرافیک آموزشی

ابتدا backend SVG یا turtle برای خط، دایره، مستطیل، رنگ، حرکت و پاک‌کردن صفحه ارائه شود. بهتر است گرافیک در پنل WebView اکستنشن دیده شود تا با RTL، Windows و Linux سازگاری بیشتری داشته باشد.

### اولویت پنجم: صدای اختیاری

پخش نت‌های ساده و WAV/OGG با یک dependency اختیاری پیاده‌سازی شود. نصب پایهٔ تیروتیر نباید برای کاربرانی که صدا یا گرافیک نمی‌خواهند سنگین شود:

```text
pip install tirotir[graphics]
pip install tirotir[audio]
```

## ۷. پیشنهاد نسخهٔ ۲٫۰

نسخهٔ ۲٫۰ می‌تواند شامل Language Server کامل، debugger، package manager، ماژول‌ها و import کنترل‌شده، type hints اختیاری، compiler یا bytecode، پروژه‌های چندفایلی، تست واحد داخل خود زبان و محیط آموزشی تعاملی باشد.

در این مرحله می‌توان syntax را با حفظ سازگاری نسخهٔ ۱ گسترش داد. پشتیبانی از کوتیشن استاندارد، ساختارهای دادهٔ غنی‌تر، exception handling و کلاس‌ها نیز در این مرحله منطقی‌تر است.

## ۸. ساختار پیشنهادی توسعهٔ آینده

```text
src/tirotir/
  lexer/
  parser/
  ast/
  semantic/
  interpreter/
  runtime/
    stdlib/
    security/
    graphics/
    audio/

vscode-tirotirLang/
```

این ساختار separation of concerns را حفظ می‌کند. زبان، runtime و رابط VS Code نباید به هم وابستگی مستقیم و کنترل‌نشده داشته باشند.

## ۹. جمع‌بندی تصمیم‌های پیشنهادی

تیروتیر برای افزودن ایموجی نیاز به کتابخانهٔ جدید ندارد؛ Unicode و خروجی امن کافی است. برای رسم، SVG در WebView بهترین گزینهٔ قابل‌حمل و turtle بهترین گزینهٔ آموزشی ساده است. برای موسیقی، backend اختیاری Python مانند pygame مناسب است، اما باید از طریق API فارسی و whitelist استفاده شود.

ترجمهٔ کل زبان به Python توصیه نمی‌شود. مفسر مستقیم فعلی باید هستهٔ اصلی باقی بماند و فقط adapterهای کنترل‌شده برای امکانات جانبی اضافه شوند. این روش امنیت، خطاهای قابل فهم و قابلیت توسعه را بهتر حفظ می‌کند.

برای راست‌به‌چپ، خروجی اصلی CLI باید UTF-8 و بدون دست‌کاری اجباری BiDi بماند. راه‌حل حرفه‌ای اکستنشن، پنل WebView با `dir="rtl"` است. این پنل باید در نسخهٔ ۱٫۱ در اولویت بالا قرار گیرد.

# پیوست انتشار نسخهٔ ۱٫۱٫۰

## قابلیت‌های پیاده‌سازی‌شده در این انتشار

نسخهٔ ۱٫۱٫۰ علاوه بر امکانات پایهٔ نسخهٔ ۱٫۰، Creative Mode را اضافه می‌کند. API گرافیکی فارسی با backend SVG شامل پنجرهٔ صحنه، حرکت، عقب‌رفتن، چرخش، تعیین جهت، قلم، رنگ، ضخامت، مربع، مستطیل، دایره و مثلث است. دستور `تکرار ... بار` نیز برای الگوهای هندسی و انیمیشن‌های مرحله‌ای اضافه شده است.

نمونهٔ گرافیکی:

```text
پنجره بازکن با ۸۰۰ و ۶۰۰
رنگ قلم برابر -آبی-
تکرار ۴ بار
    حرکت با ۱۰۰
    چرخش با ۹۰
```

اجرای این برنامه از CLI با `--scene scene.svg` فایل SVG تولید می‌کند. این انتخاب باعث شده backend گرافیک از lexer و parser جدا بماند.

نسخهٔ ۱٫۱٫۰ همچنین تولید نت ساده به‌صورت WAV را بدون dependency اجباری اضافه کرده است:

```text
نت بنواز با ۴۴۰ و ۰٫۵
```

برای رابط گرافیکی دسکتاپ، backend اختیاری Tkinter اضافه شده است. API شامل `پنجره بساز`، `برچسب بساز`، `دکمه بساز`، `ورودی بساز` و `نمایش پنجره` است. callback دکمه و layout رویدادمحور کامل به نسخهٔ بعد موکول شده است.

## خروجی راست‌به‌چپ اکستنشن

اکستنشن `tirotirLang` اکنون فرمان **«اجرا در پنل فارسی راست‌به‌چپ»** دارد. این پنل WebView با `dir="rtl"`، `lang="fa"`، `unicode-bidi: plaintext` و فونت فارسی، خروجی و خطا را نمایش می‌دهد. ترمینال به‌عنوان fallback باقی می‌ماند. تغییر جهت فقط در لایهٔ نمایش انجام می‌شود و ترتیب منطقی نویسه‌های کد دست‌کاری نمی‌شود.

## آزمون نسخهٔ ۱٫۱٫۰

مجموعهٔ آزمون به ۲۰۲ تست خودکار موفق رسیده است. ۷۱ برنامهٔ نمونه در repository وجود دارد و نام فایل‌های آن‌ها انگلیسی استاندارد است. تست‌های جدید API SVG، شکل‌ها، تکرار، تولید WAV و Unicode ایموجی را پوشش می‌دهند. نمونهٔ رسمی زبان، نمونه‌های پایه و نمونه‌های creative از طریق CLI بررسی شده‌اند.

## GUI و ساخت EXE

رابط گرافیکی با Tkinter اختیاری است و در `src/tirotir/core.py` به‌صورت lazy import بارگذاری می‌شود. بنابراین نصب پایهٔ زبان به dependency سنگین نیاز ندارد. راهنمای کامل Windows و PyInstaller در `docs/windows-exe-and-gui-fa.md` قرار دارد. ساخت فایل `.exe` باید روی Windows انجام شود:

```powershell
py -m pip install pyinstaller
py -m pip install .
pyinstaller --clean --onefile --name tirotir --paths src tools\tirotir_launcher.py
```

## وضعیت باقی‌مانده

در نسخهٔ ۱٫۱٫۰، پنجره و عناصر پایهٔ Tkinter قابل ایجاد هستند، اما رویدادهای دکمه، اتصال دادهٔ ورودی به متغیر، طراحی drag-and-drop، canvas مشترک با SVG و installer گرافیکی نهایی هنوز باقی مانده‌اند. همچنین پخش فایل موسیقی خارجی عمداً experimental است؛ تولید نت WAV پایدار و قابل تست است.

## مسیر پیشنهادی ۱٫۲ و ۲٫۰

نسخهٔ ۱٫۲ باید رویدادهای GUI، callbackهای فارسی، canvas تعاملی، diagnostics لحظه‌ای، completion، hover، formatter AST-based و اجرای مرحله‌ای را تکمیل کند. نسخهٔ ۲٫۰ می‌تواند Language Server کامل، debugger، پروژه‌های چندفایلی، import whitelist شده، package manager کوچک و backend بازی دوبعدی رویدادمحور داشته باشد.
