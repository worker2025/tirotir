# طرح طراحی KI-1 — ابهام literal متنی و تفریق

**وضعیت:** طراحی پیش از اصلاح؛ هیچ تغییر lexer برای KI-1 در این مرحله اعمال نشده است.
**HEAD مبنا:** `e3c1cd822aea5adf6c596345219329df35aef1b`
**نسخهٔ مرجع:** Tirotir 1.1.0
**قاعدهٔ حفاظت:** نمونهٔ سالم `چاپ -سلام دنیا-` باید بدون تغییر خروجی `سلام دنیا` بدهد.

## ۱. شواهد واقعی tokenizer

### متن سالم

منبع:

```text
چاپ -سلام دنیا-
```

توکن‌های واقعی:

```text
WORD    چاپ
STRING  سلام دنیا
NEWLINE
EOF
```

خروجی اجرایی: `سلام دنیا`.

### تفریق فاصله‌دار

منبع:

```text
چاپ ۵ - ۳ + ۲ - ۱
```

توکن‌های واقعی:

```text
WORD   چاپ
NUMBER 5
OP     -
NUMBER 3
OP     +
NUMBER 2
OP     -
NUMBER 1
NEWLINE
EOF
```

خروجی اجرایی: `3`.

### تفریق فشرده

منبع:

```text
چاپ ۵-۳+۲-۱
```

توکن‌های واقعی:

```text
WORD   چاپ
NUMBER 5
STRING ۳+۲
NUMBER 1
NEWLINE
EOF
```

خروجی اجرایی فعلی: `5`.

علت مستقیم در lexer فعلی این است که هنگام دیدن `-`، اگر نویسهٔ بعدی فاصله نباشد و یک خط تیرهٔ بسته‌شدن پیدا شود، محتوای میان دو خط تیره `STRING` می‌شود. این علت با token dump بالا اثبات شده است؛ هنوز هیچ اصلاح precedence یا grammar اعمال نشده است.

## ۲. قرارداد پیشنهادی زبان

### ۲.۱ literal متنی legacy

قرارداد فعلی `-متن-` باید برای برنامه‌های نسخهٔ ۱ حفظ شود، ازجمله:

- `چاپ -سلام دنیا-`؛
- متن فارسی چندکلمه‌ای؛
- متن دارای نیم‌فاصله؛
- متن دارای رقم فارسی؛
- متن دارای خط تیرهٔ escaped با `\-`؛
- متن در جایگاه expression پس از `چاپ`، `برابر` و آرگومان تابع.

literal خالی `--` در grammar فعلی literal معتبر نیست. تا زمان تصمیم مستقل دربارهٔ empty string، نباید رفتار آن به‌صورت ضمنی تغییر کند.

### ۲.۲ تفریق

عملگر تفریق باید در این موارد بدون نیاز به فاصله معتبر باشد:

- `۵-۳`؛
- `الف-ب`؛
- `۵-۳+۲-۱`؛
- `الف--۳` در صورت پشتیبانی از unary negative؛
- expressionهایی که بعد از `]` یا `)` با تفریق ادامه می‌یابند.

وقتی lexer بتواند یک `-` را هم آغاز literal و هم عملگر تشخیص دهد، نباید بی‌صدا یکی را انتخاب کند و مقدار دیگری تولید شود. انتخاب پیشنهادی برای حالت مبهم، diagnostic مشخص یا نیاز به syntax صریح است؛ silent wrong result قابل قبول نیست.

### ۲.۳ syntax صریح آینده

برای برنامه‌های جدید، اضافه‌کردن string delimiter صریح مانند `"متن"` یا `«متن»` می‌تواند ambiguity را حذف کند؛ اما این قابلیت نباید جایگزین ناگهانی `-متن-` شود و در این مرحله نباید به lexer اضافه شود.

## ۳. ماتریس موارد مرزی

| # | منبع | انتظار/تصمیم پیشنهادی | وضعیت فعلی |
|---:|---|---|---|
| 1 | `چاپ -سلام دنیا-` | literal سالم، خروجی دقیق | سالم؛ باید حفظ شود |
| 2 | `چاپ -فارسی‌زبان-` | حفظ U+200C | با KI-2 اصلاح شده |
| 3 | `چاپ -۱۲۳-` | literal متنی، نه عدد | باید characterization شود |
| 4 | `چاپ --` | empty string فقط با قرارداد صریح | فعلاً literal معتبر نیست |
| 5 | `چاپ -الف\-ب-` | متن `الف-ب` | escape در lexer موجود است؛ باید regression شود |
| 6 | `چاپ ۵ - ۳` | تفریق با فاصله، خروجی ۲ | سالم |
| 7 | `چاپ ۵-۳` | تفریق فشرده، خروجی ۲ | فعلاً ambiguous و ناسالم |
| 8 | `چاپ ۵-۳+۲-۱` | محاسبهٔ چپ‌گرا، خروجی ۳ | فعلاً خروجی ۵ و بازتولیدشده |

| 10 | `چاپ - ۵` | unary negative با فاصله، یا diagnostic یکسان | باید characterization شود |
| 11 | `چاپ الف-ب` | تفریق شناسه‌ها | باید پس از تصمیم lexer آزموده شود |
| 12 | `چاپ [۵]-۳` | تفریق پس از index/list | باید پس از تصمیم lexer آزموده شود |
| 13 | `چاپ (۵)-۳` | تفریق پس از پرانتز | باید پس از تصمیم lexer آزموده شود |

## ۴. گزینه‌های طراحی و ریسک سازگاری

### گزینهٔ A — حفظ delimiter قدیمی و الزام فاصله برای تفریق

در این مدل `۵-۳` همچنان ambiguous یا نامعتبر می‌ماند و مستندات الزام می‌کنند اطراف تفریق فاصله باشد.

- کمترین تغییر کد؛
- بیشترین سازگاری با تشخیص فعلی متن؛
- اما با انتظار طبیعی کاربران از عملگرهای فشرده ناسازگار است؛
- silent wrong result باید با diagnostic جایگزین شود.

### گزینهٔ B — تشخیص context در lexer

lexer بر اساس token قبلی، جایگاه expression و token بعدی تصمیم می‌گیرد که `-` عملگر است یا آغاز متن. برای نمونه، پس از `NUMBER` یا `WORD`، `-` به‌طور پیش‌فرض عملگر و پس از keywordهایی مانند `چاپ` یا `برابر` نامزد آغاز متن باشد.

- می‌تواند تفریق فشرده را پشتیبانی کند؛
- نمونهٔ canonical با فاصله حفظ می‌شود؛
- اما lexer را context-sensitive می‌کند؛
- متن‌های legacy بدون فاصله مانند `چاپ-سلام-` ممکن است تغییر کنند؛
- به matrix کامل و migration note نیاز دارد.

### گزینهٔ C — delimiter صریح برای متن‌های جدید

`"متن"` یا `«متن»` برای کد جدید اضافه شود و `-متن-` به‌عنوان legacy باقی بماند.

- کمترین ریسک برای برنامه‌های قدیمی؛
- ambiguity کد جدید را حذف می‌کند؛
- اما مشکل کد legacy فشرده را به‌تنهایی حل نمی‌کند؛
- در این مرحله قابلیت جدید اضافه نمی‌شود و فقط به‌عنوان مسیر آینده ثبت می‌شود.

## ۵. پیشنهاد کم‌خطر

پیشنهاد مرحله‌ای و کم‌خطر این است:

1. ابتدا تمام ۱۴ مورد بالا را characterization کنیم، بدون تغییر lexer؛
2. نمونهٔ `چاپ -سلام دنیا-`، متن دارای نیم‌فاصله و escape را به‌عنوان قرارداد legacy قفل کنیم؛
3. برای `۵-۳` و حالت‌های مشابه تصمیم رسمی بگیریم که پشتیبانی می‌شوند یا diagnostic می‌گیرند؛
4. اگر تفریق فشرده الزامی است، ابتدا گزینهٔ B را در یک parser/tokenizer آزمایشی یا feature branch جدا پیاده کنیم؛
5. کل examples و regression نسخهٔ 1.1.0 را با نسخهٔ آزمایشی مقایسه کنیم؛
6. فقط پس از مشاهدهٔ نبود regression، تغییر اصلی lexer را در commit مستقل انجام دهیم.

در این مرحله **گزینهٔ A همراه با diagnostic صریح** کمترین ریسک فوری را دارد، اما از نظر تجربهٔ زبان بهترین راه‌حل نهایی نیست. گزینهٔ B نامزد اصلاح P0 است، ولی تا تکمیل matrix نباید اجرا شود. گزینهٔ C برای نسخهٔ آینده مناسب است و نباید بهانه‌ای برای شکستن delimiter فعلی شود.
